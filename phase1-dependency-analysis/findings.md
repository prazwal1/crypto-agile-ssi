# Phase 1 Findings: Cryptographic Dependency Analysis (RQ1)

Baseline: `manifest.tsv`. Static findings (F1 to F8) were confirmed by reading the source, not only by scanner matches. Runtime findings (F9 onward) cite files in `../evidence/`.

| F9 | S1/S3 | The deployed FarmerCredential accepts holder proofs signed with RS256 or ES256 only, and binds the holder with `did:jwk`. | F11 | S2/S3 | Two independent verifiers act on every credential in the default flow: the wallet verifies on receipt (vc-verifier, F6) and Inji Verify verifies on presentation; each resolves the issuer `did:web` document over HTTPS at verification time. Both accepted an `assertionMethod` that lists the DID rather than the verification method id (D-07) | `../evidence/2026-10-13-reference-run/` (did.json fetched 20:22:48 and 20:23:33; wallet `isVerified: true`); `inji-verify-result.png` | A new proof suite must be understood by both verifier implementations before the wallet will even store a credential; issuer key rotation is visible to both through the DID document |
| F12 | S1/S3 | On the issuer, one signature algorithm is spread over 12 registries in two repositories: 3 in data or config (`credential_config`, suite-to-alg map, alg-to-key map), 8 in code (Certify proof generators or the danubetech cryptosuite list, the DID verification-method switch, and in keymanager the reference-id constants, the key-generation if-chains, `SignatureProviderEnum`, `AlgorithmInstanceEnum`, `SignatureAlgorithmIdentifyEnum` with `SignatureUtil`, and the COSE switch), and the JCA provider library. | F13 | S1 | Keymanager encodes the key type in the reference-id string (`ED25519_SIGN`, `EC_SECP256R1_SIGN`, `EC_SECP256K1_SIGN`, blank for RSA) and falls back silently: missing algorithm becomes PS256, unrecognised reference id maps to RS256/PS256, unknown COSE input becomes PS256, an unknown application id switches to the default signing key | keymanager `SignatureServiceImpl.java:282`, `:667`; `SignatureUtil.java:217`; `SignatureAlgorithmIdentifyEnum.java:10`; `CoseSignatureServiceImpl.java:404` | Algorithm identity is implicit in a naming convention, and errors degrade to a classical default instead of failing. A crypto-agile design must make the algorithm explicit and fail closed (RQ2) |
| F14 | S1 | Issuer keys sit in a classical hierarchy: application master keys are RSA-2048 with `SHA256withRSA` certificates; the Ed25519 VC signing key is generated in software and stored in the database encrypted under the RSA master key | keymanager `KeymanagerServiceImpl.java:372`, `:393`, `:415`; `env/stack/config/certify-default.properties:82-102` | Swapping the VC signature to ML-DSA would leave key protection and key certification on RSA, so a quantum attacker holding the database could recover signing keys. | F15 | S2 | The issuer DID document is generated with `authentication` and `assertionMethod` hard-coded to the DID itself, and the verification-method type chosen by a switch over four algorithms (Ed25519VerificationKey2020, EcdsaSecp256r1VerificationKey2019, EcdsaSecp256k1VerificationKey2019, RsaVerificationKey2018) | `inji-certify/.../utils/DIDDocumentUtil.java:62-63`, `:109-125` | Root cause of D-07. | F16 | S1/S3 | The deployed issuer JVM carries three BouncyCastle copies: `bcprov-jdk18on-1.78.1`, `bcprov-jdk15on-1.70` and an unversioned shaded copy inside the mock plugin jar. None contains final ML-DSA (FIPS 204) or SLH-DSA (FIPS 205); only 1.78.1 has the pre-standard Dilithium and SPHINCS+ classes | `../evidence/2026-10-13-certify-image-libs/` (`bouncycastle-check.txt`, `crypto-libs.txt`) | A PQ issuer needs a newer provider, and with three copies on the classpath which one the JCA resolves is a deployment detail the design must pin down (provider selection, RQ2; D-04) |
| F17 | S3 | On iOS the wallet does not verify Ed25519Signature2020, mdoc or SD-JWT credentials: it returns a successful verification result without checking the signature (comment: the bundled library cannot verify Ed25519Signature2020) | `inji-wallet/shared/vcjs/verifyCredential.ts:82-95`; `../evidence/2026-10-13-inventory-review/excerpts.md` R1 | A suite the code cannot handle is treated as valid (fail open). Out of the Android prototype's scope, but direct evidence that unsupported algorithms are a security risk, not only a feature gap (RQ2: fail closed) |
| F18 | S3 | The issuer and the wallet's verifier library disagree on what is valid. Certify can issue EcdsaSecp256r1Signature2019 (ES256) and Data Integrity cryptosuites; vc-verifier accepts only 4 JWS algorithms (PS256, RS256, EdDSA, ES256K) and 4 proof types (RsaSignature2018, Ed25519Signature2018/2020, EcdsaSecp256k1Signature2019) and rejects the rest before checking signatures. Separately, any `proofValue` proof is verified as Ed25519 whatever its type. Static result, not run. Version note (D-08, C-10): the wallet bundles vc-verifier 1.6.0, whose `SignatureFactory` also maps ES256 to the secp256k1 verifier (`SignatureFactory.kt:22`). Inji Verify 0.18.2 bundles 1.8.1, which maps ES256 correctly, accepts EcdsaSecp256r1Signature2019 and chooses the algorithm from the proof type (unknown suite fails); its JWS allow-list is unchanged. The two verifiers in the flow (F11) therefore accept different sets | `../evidence/2026-10-13-inventory-review/excerpts.md` R2 to R6; `env/stack/config/certify-default.properties:197-208`; `../evidence/2026-10-14-verify-version-diff/README.md` | Even among classical algorithms the registries are not in step; a credential the issuer offers may be refused by the wallet. Adding ML-DSA must update the verifier's allow-lists, its dispatch on proof shape, and the issuer together (F6, F12) |
| F19 | S1/S3 | Mimoto (and the wallet, F9) negotiate the holder-proof algorithm from issuer metadata: Mimoto takes the first match of a configured priority list (ED25519, ES256K, ES256, RS256) against `proof_signing_alg_values_supported`, and if nothing matches it still sends an Ed25519 proof. Mimoto pre-generates a proof key for each of its four algorithms per wallet | `../evidence/2026-10-13-inventory-review/excerpts.md` R7, R8 | A working negotiation precedent the CSL can reuse, with a fail-open fallback to remove. Pre-generating one key per algorithm grows linearly with the algorithm list (relevant to ML-DSA key and storage size) |
| F20 | S2/S3/S4 | Fixed single-algorithm choices outside the credential itself: OpenID4VP request objects are verified with Ed25519 keys only (others fail closed); Inji Verify requires its own request-signing key to be Ed25519; OpenID4VP response encryption uses ECDH-ES with X25519; Certify accepts external access tokens only as ES256, RS256 or PS256 and signs its own as RS256 | `excerpts.md` R9, R10, R14; `inji-verify/.../P12KeyExtractor.java:55-64`; issuer-signing-path C8 | The presentation channel and OAuth layer carry their own classical algorithms. A PQ credential still travels inside an Ed25519-signed request and an X25519-encrypted response |
| F21 | S3 | The same cryptosuite is mapped to different algorithms in two configs shipped by the Certify project: the packaged default maps `ecdsa-rdfc-2019` and `ecdsa-jcs-2019` to ES256, the injistack docker-compose config (copied into `env/stack`) maps them to ES256K. The W3C ECDSA cryptosuites are defined for P-256 and P-384, not secp256k1 | `inji-certify/certify-service/src/main/resources/application-local.properties:40-41`; `inji-certify/docker-compose/docker-compose-injistack/config/certify-default.properties:194-195`; `env/stack/config/certify-default.properties:204-205` | Algorithm meaning lives in hand-maintained config maps that already drift; one authoritative registry definition is needed (F12, R-03) |
| F22 | S4 | In the pre-authorized code flow Certify serialises every credential claim into the access token's `sub` (signed, not encrypted), so the bearer token grows with the claims. Two layers each reject headers over 8 KB by default: nginx rejected a 45 KB token (24 KB face photo); after raising nginx and shrinking the photo, Certify's own Tomcat rejected an 11.9 KB token ("Request header is too large") | `inji-certify/certify-service/.../PreAuthorizedCodeService.java:390-419`, `.../utils/AccessTokenJwtUtil.java:83-110`; `evidence/2026-10-14-reissue-face/certify-nginx.log` (token 45239 bytes, credential 400), `logcat.txt:4397`; `evidence/2026-10-14-reissue-face-2/certify.log` (Tomcat `Http11InputBuffer`, 12:27:48) | Transport limits are a hidden size budget. Also exposes all claims, including biometrics, to anyone holding the token |
| F23 | S1/S3 | The wallet chooses the holder key separately for issuance and presentation, and nothing links the two. Issuance picks the first key in the user's key order that the issuer allows (`selectCredentialRequestKey`); FarmerCredential allows RS256/ES256, so the credential was bound to the hardware P-256 key. OpenID4VP signs every `ldp_vc` presentation with the Ed25519 key, fixed in the machine's initial context, and builds the VP holder `did:jwk` from it. Inji Verify 0.18.2 rejected both presentations: `ERR_HOLDER_BINDING_CHECK_FAILED`, VP holder OKP/Ed25519 vs VC subject EC/P-256. The limitation is wallet-side: Inji Verify's vc-verifier 1.8.1 resolves Ed25519 and P-256 holder keys and accepts JsonWebSignature2020 with EdDSA, ES256K or ES256 (`PresentationVerifier.kt:332-333`, `:512+`), so a P-256 presentation would have been accepted | `inji-wallet/shared/openId4VCI/Utils.ts:432-447`; `machines/openID4VP/openID4VPModel.ts:80`; `machines/openID4VP/openID4VPServices.ts:106-107`; `shared/openID4VP/OpenID4VPHelper.ts:60-80`; `evidence/2026-10-14-presentation-run-2/verify-service.log` (12:44:38, 12:45:58); `evidence/2026-10-14-presentation-export/TRACE.md` (failed vs successful key pairs); `../evidence/2026-10-14-verify-version-diff/README.md` | Creation coupling at runtime: the key a credential is bound to is not recorded and reused, so any issuer that does not offer Ed25519 yields credentials the wallet cannot present. An agile design needs the binding key (and its algorithm) stored with the credential and selected for presentation. Also forces the software Ed25519 key over the hardware key (F3) for ldp_vc presentations |
